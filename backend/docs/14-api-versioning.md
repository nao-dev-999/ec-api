# 14. APIバージョニングと互換性方針

> [← インデックスに戻る](../コーディング規約.md)

---

## 基本方針

URLパスにバージョンを含めない（現状 `/api/admin/products` であり `/api/v1/admin/products` ではない）。
**後方互換を壊さない変更はバージョンを上げずに追加し、壊れる変更が必要になった時点で初めてバージョニングを導入する。**
最初から `v1` を付けて将来の `v2` を前提に設計すると、使われないまま複数バージョンの保守コストだけが残ることが多いため。

---

## 互換性のある変更・ない変更

```
// ✅ 後方互換あり（バージョンアップ不要）
- レスポンスに新しいフィールドを追加する
- リクエストに任意（デフォルト値あり）のフィールドを追加する
- 新しいエンドポイントを追加する
- 新しいenum値を追加する（クライアントが未知の値を無視できる前提）

// ❌ 後方互換なし（バージョンアップまたは移行計画が必要）
- レスポンスのフィールドを削除・リネームする
- フィールドの型を変える（例: Integer → String）
- 必須リクエストパラメータを追加する
- エンドポイントのURL・HTTPメソッドを変更する
- enumの値を削除・リネームする
- エラーコード（`code`）の意味を変える
```

新しいenum値の追加に備えて、クライアント側は「未知のenum値が来たらデフォルト扱いにする」実装を基本とする。Web/モバイル双方のフロントエンド実装規約にも反映すること。

## 破壊的変更が必要になった場合

### バージョニング方式: URLパスバージョニング

```
/api/v1/admin/products
/api/v2/admin/products
```

ヘッダーバージョニング（`Accept: application/vnd.ecapi.v2+json`）やクエリパラメータ方式は採用しない。ログ・ドキュメント・ルーティング設定上の可読性を優先する。

### 単位

エンドポイント単位でバージョンを切る。API全体を一括で `v2` に上げない（移行コストが大きく、全エンドポイントが同時に壊れるリスクがあるため）。

```
// ✅ 変更が必要なエンドポイントのみ新バージョンを用意する
POST /api/v1/orders   // 既存のまま維持
POST /api/v2/orders   // 新しい形式

// ❌ 無関係なエンドポイントまで一律 v2 化しない
```

### 実装

Controller クラスごとバージョンを分ける。新旧バージョンが同一Serviceを呼ぶ場合はController層のマッパーで差異を吸収し、Service層にバージョン分岐を持ち込まない。

```java
// ✅ Controller層でリクエスト/レスポンスの形式差異を吸収する
@RestController
@RequestMapping("/api/v2/orders")
public class OrderV2Controller {
    private final OrderService orderService; // v1と共通のServiceを使う
    // v2固有のリクエスト/レスポンス変換のみここに書く
}

// ❌ Service層に if (version == 2) のような分岐を持ち込まない
```

## 廃止（Deprecation）のプロセス

1. 新バージョンのリリース時、旧バージョンのレスポンスヘッダーに `Deprecation: true` と `Sunset: <廃止予定日>` を付与する
2. 廃止予定日はクライアント（フロントエンド・社内バッチ・外部パートナー）の移行に十分な期間を確保する（目安: 社内クライアントのみなら1スプリント以上、外部公開APIなら3ヶ月以上）
3. OpenAPI定義上は `@Deprecated` を付与し、Swagger UIで非推奨である旨を明示する
4. 廃止日到達後、旧エンドポイントは410 Goneを返すようにしてから一定期間後に削除する（即削除しない）

```java
@GetMapping
@Deprecated(since = "2026-10", forRemoval = true)
public ResponseEntity<List<OrderResponseV1>> listOrdersV1() {
    response.setHeader("Deprecation", "true");
    response.setHeader("Sunset", "Wed, 31 Dec 2026 00:00:00 GMT");
    // ...
}
```

## OpenAPI定義の後方互換チェック

CIに破壊的変更の検知を組み込む。`main` ブランチの `v3/api-docs` のスナップショットと差分を取り、互換性のない変更（必須フィールド追加・フィールド削除等）がある場合はCIを失敗させることを検討する。導入時期は実際に外部公開APIができたタイミングで判断する。

## チェックリスト

- [ ] 変更が後方互換を壊すかどうかを事前に判定した
- [ ] 破壊的変更の場合、エンドポイント単位でバージョンを切った（API全体を一括で上げていない）
- [ ] 旧バージョンに `Deprecation` / `Sunset` ヘッダーを付与した
- [ ] Service層にバージョン分岐を持ち込んでいない
